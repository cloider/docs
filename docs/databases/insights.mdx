Insights show how much of its plan a database uses: CPU, memory, storage, disk reads and writes, network traffic and open connections. Cloider samples every running database once a minute and keeps daily figures for the last 31 days. Use them to see whether a database is the right size and when to [resize](/databases/resize) it.

Insights are informational only. A database is billed by its plan, not by its measured usage.

## At a glance

| | |
| --- | --- |
| **Metrics** | CPU, memory, storage used, disk read, disk write, network in, network out, connections |
| **Sampling** | Once a minute while the database is running. Nothing is sampled while it is paused |
| **History** | One average, highest and lowest value per metric and day, for the last 31 days |
| **Where** | The **Insights** tab, `cloider db insights`, `GET /api/databases/<id>/insights`, the `get_database_insights` MCP tool |
| **Cost** | Free |

## What each metric means

| Metric | Unit | What it measures | When to act |
| --- | --- | --- | --- |
| **CPU** | Cores (millicores in the API, 1000 = 1 core) | Processor time the database uses | Averages near the plan's vCPU at busy times |
| **Memory** | GB (MiB in the API) | RAM the database server uses, including caches | Stays near the plan's RAM, or Redis data approaches it |
| **Storage Used** | GB (GiB in the API) | Space your data takes on the volume, not the volume's size | Approaches the plan's storage. A full disk stops writes |
| **Disk Read**, **Disk Write** | KB/s or MB/s (bytes per second in the API) | How much data is read from and written to the volume | High reads with high memory use can mean the working set doesn't fit in RAM |
| **Network In**, **Network Out** | KB/s or MB/s (bytes per second in the API) | Traffic received from and sent to clients | Unexpected spikes can mean a runaway query or a client fetching too much |
| **Connections** | Count | Open client connections. The **max** next to it is the most the server accepts | Stays close to the max: use a connection pool or a larger plan |

The values are averages over each sampled minute, and each day keeps its average, its highest (peak) and its lowest value. Connections made by Cloider's own monitoring aren't counted.

## Reading the charts

- **Average vs peak.** A day's average shows normal load, its peak the busiest minute. A high peak with a low average is a short burst, such as a nightly job, and usually doesn't need a bigger plan.
- **Storage only grows with your data.** Storage Used counts the data on the volume, not the volume's size. Deleted rows may not free space right away, depending on the engine (PostgreSQL reclaims it with `VACUUM`, MySQL with `OPTIMIZE TABLE`).
- **Memory looks high on a healthy database.** Databases keep recently used data in RAM as a cache, so memory close to the plan's RAM is normal for PostgreSQL, MySQL and MongoDB. Watch for slow queries and high disk reads together with it. For Redis, memory is the data itself: when it reaches the plan's RAM, resize.
- **Connections near the max.** Every open connection counts, including idle ones held by connection pools. See [how many connections a database handles](/databases/connect#how-many-connections-can-my-database-handle).
- **Gaps.** Days when the database was paused, or before it existed, have no bars.

## Troubleshooting

### Performance insights become available once sufficient data has been collected.

The database is new or has been paused, and no sample has been taken yet. Samples are taken once a minute while the database is running.

### Connections show "-" with "Not available yet"

Some older databases don't report a connection count yet. The other metrics are still collected.

### Could not load insights. Please try again later.

The dashboard couldn't load the insights. Reload the page. If it persists, use `cloider db insights <database> -o json` or [contact support](/account/support).
