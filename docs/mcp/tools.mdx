This page lists every tool the Cloider MCP server (`cloider mcp`) offers, grouped by toolset. For each tool you get the description the AI agent sees, its parameters with their types and whether they are required, what kind of change it makes, whether repeating it is safe, the MCP annotations your client uses to decide when to ask you first, and the [`cloider` CLI](/cli/overview) command it runs. Setting the server up is covered in [Set up the MCP server](/mcp/setup).

- **Read only** tools change nothing. They are the only tools `cloider mcp --read-only` offers.
- **Changes resources** tools create or update something but don't delete anything.
- **Destructive** tools delete or replace something, or run arbitrary commands (the three exec tools), and carry `destructiveHint`.
- Pick toolsets with `cloider mcp --toolsets account,apps,...`. See [Safety and permissions](/mcp/safety-and-permissions).

## How to read this reference

Each tool has a table like this:

| Column | Meaning |
| --- | --- |
| **Effect** | **Read only**, **Changes resources** or **Destructive** |
| **Idempotent** | **Yes** when calling it again with the same arguments changes nothing more, so a client may retry it safely |
| **Annotations** | The MCP tool annotations set to `true`: `readOnlyHint`, `destructiveHint`, `idempotentHint`. `openWorldHint` is `false` on every tool, because the tools only reach your Cloider account |
| **Runs** | The CLI command the tool runs, linked to its reference |

And a parameter table. Parameter names are the exact JSON keys of the tool's arguments. Types are JSON schema types: `object` parameters take `{"KEY": "value"}` maps of strings, and the JSON parameters (`policy`, `rules`) take a JSON document. The server is lenient where models tend to slip: a number sent as a string, `"true"` for a boolean, or one string where a list is expected are all accepted. An unknown parameter fails with `unknown argument "<name>", <tool> takes: ...`, and a missing required one with `<name> is required`.

## Behavior every tool shares

- **Names or ids.** Every resource parameter (`cluster`, `database`, `bucket`, `project`, `app`) takes the resource's name or its id, the same as the CLI.
- **Answers are JSON.** A tool answers with the command's JSON output, compacted, followed by anything the command printed as notes (its success line and any warnings). Output over 1 MiB is cut, keeping the start, or for logs the end. A tool whose command prints nothing answers `Done.`
- **Errors** come back as a failed tool call with the command's error message, for example the API's validation message, so the agent can correct its arguments and try again.
- **Waiting.** Tools that create, pause, resume or delete something take `wait`. Without it they return while the change is under way, and the matching `get_*` tool shows the status. With `wait: true` they wait up to 15 minutes.
- **Progress.** When the client asks for progress (by sending a `progressToken` with the call), the lines the command prints while it runs are sent as MCP progress notifications, at most one a second, with a heartbeat every 15 seconds when nothing is printed. A client can then show a deploy's build as it happens.
- **No prompts.** Commands run with `--yes`, so nothing asks for confirmation inside the tool. Asking you is your MCP client's job, guided by the annotations.
- **Local files.** Paths (`dir`, `paths`, `dest`, `file`, `attachments`) are on the machine the MCP server runs on, which is usually your computer.
- **Concurrency.** At most 4 tool commands run at once, to stay inside the API's rate limit of 100 requests a minute.
- **Cancelling** a tool call from the client stops its command, as Ctrl-C would.

## Account tools (account)

The `account` toolset tells the agent who it is acting as and what things cost. Start a session with `whoami`: it says which account the token belongs to, the role, and whether the token can only read. Members and API tokens can be listed but not changed: adding members, changing roles and creating or revoking tokens are dashboard only, see [Access control](/account/access-control) and [API tokens](/account/api-tokens).

Tools: `whoami`, `get_usage`, `get_billing`, `get_pricing`, `list_members`, `list_api_tokens`.


### whoami

Who the tools act as: the user, the account, the role, and whether the API token can only read.

| Effect | Idempotent | Annotations | Runs |
| --- | --- | --- | --- |
| Read only | Yes | `readOnlyHint`, `idempotentHint` | [`cloider whoami`](/cli/commands/account) |

No parameters.

### database_exec

Run a query with the database's own client, running next to it and already logged in; trusted sources don't apply. PostgreSQL runs it with psql -c, MySQL with mysql -e, Redis as a redis-cli command ("GET key"), MongoDB as mongosh --eval JavaScript. script runs a whole script instead (a PostgreSQL script stops at its first error). Returns `{exit_code, stdout, stderr, timed_out}`.

:::note
Give either `query` or `script`, not both (`give either query or script`).
:::

| Effect | Idempotent | Annotations | Runs |
| --- | --- | --- | --- |
| Destructive | No | `destructiveHint` | [`cloider db exec`](/cli/commands/db) |

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| `database` | string | Yes | Name or id of the database. |
| `query` | string | No | The query or command. |
| `script` | string | No | A script to run instead of a query, up to 2 MiB. |
| `timeout_seconds` | integer | No | Stop it after this long, 1 to 3600 seconds (default 600). |

## App tools (apps)

The `apps` toolset deploys and runs [apps](/apps/overview): deploy a directory from the machine the MCP server runs on, create an app from a GitHub, GitLab or Bitbucket repository, follow builds, read logs, manage environment variables, build args and build environments, run commands in the app's container, and pause, resume or delete apps. `deploy_app` and `create_app_from_git` follow the build until the app is up, reporting progress as they go, unless `detach` is set.

Tools: `list_apps`, `get_app`, `deploy_app`, `create_app_from_git`, `pause_app`, `resume_app`, `delete_app`, `update_app_settings`, `update_app_git`, `get_app_logs`, `list_app_builds`, `get_app_build_logs`, `retry_app_build`, `list_app_variables`, `get_app_variable`, `set_app_variables`, `unset_app_variables`, `app_exec`, `list_git_installations`, `list_git_repositories`, `list_git_branches`, `connect_git_provider`, `disconnect_git_installation`.

### deploy_app

Deploy a directory on this machine as an app. The first deploy zips it (leaving out what .gitignore and .cloiderignore list, up to 2000 files and 100 MB), detects the language, framework and port, creates the app with a free subdomain, and links the directory to it in .cloider/app.json; later deploys from the directory build a new version. With git, builds the latest commit of a git app's branch instead. Follows the build until the app is up and answers its URL, unless detach. The params for a new app are ignored when deploying to an existing one.

:::note
`dir` is required unless `git` is true, and `git` needs `app`. `dir` must be an absolute path on the machine the MCP server runs on.
:::

| Effect | Idempotent | Annotations | Runs |
| --- | --- | --- | --- |
| Changes resources | No | none | [`cloider deploy`](/cli/commands/deploy) |

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| `dir` | string | No | Absolute path of the directory to deploy. |
| `app` | string | No | Deploy to this existing app instead of the one the directory is linked to. |
| `git` | boolean | No | Build the latest commit of the app's git branch instead of uploading, needs app. |
| `name` | string | No | App name for a new app (default: what detection finds, else the directory or repository name). |
| `port` | integer | No | Port a new app listens on (default: detected, else 8080). |
| `start_command` | string | No | Command a new app starts with (default: detected). |
| `subdomain` | string | No | Free subdomain a new app is served on, a label or a full name (default: `<name>-<random>`). |
| `no_subdomain` | boolean | No | Don't claim a free subdomain for a new app. |
| `env` | object | No | Environment variables of a new app, `{"KEY": "value"}`. |
| `secret_env` | object | No | Secret environment variables of a new app, never listed back. |
| `build_args` | object | No | Dockerfile build args of a new app (ARG NAME). |
| `secret_build_args` | object | No | Dockerfile build secrets of a new app, for RUN --mount=type=secret,id=NAME,env=NAME. |
| `build_env` | object | No | Buildpack build variables of a new app, for an app without a Dockerfile. |
| `secret_build_env` | object | No | Secret buildpack build variables of a new app. |
| `detach` | boolean | No | Return once the build starts instead of following it until the app is up. |

## Domain, DNS and target tools (domains)

The `domains` toolset claims free `cloider.app` subdomains, adds custom domains, manages a custom domain's [DNS records](/domains/dns-records), and routes paths of a domain to an app or a cluster Service with [targets](/domains/targets). A custom domain comes with an A record for the domain itself that points at Cloider, but a target doesn't add records, so routing a subdomain such as www usually takes a `create_dns_record` too, see [Add a custom domain](/domains/add-a-custom-domain).

There is no tool that lists a domain's targets. Keep the id from `create_domain_target`'s answer, or list them with `cloider target list <domain> -o wide`.

Tools: `list_domains`, `get_domain`, `check_domain_availability`, `create_domain`, `delete_domain`, `list_dns_records`, `create_dns_record`, `update_dns_record`, `delete_dns_record`, `create_domain_target`, `update_domain_target`, `delete_domain_target`.

## Commands that have no tool

Some CLI commands are interactive or only make sense in a terminal, so `cloider mcp` doesn't offer them: `cloider cluster shell`, `cloider db shell`, `cloider app shell`, `cloider db connect`, `cloider login`, `cloider logout`, `cloider profile`, `cloider update`, `cloider app open`, `cloider app link` and `cloider registry login`. Adding members, changing roles and creating or revoking API tokens aren't tools either, because the API only takes those from the dashboard.
