The **Insights** tab shows how much traffic an app serves and what it uses and costs: requests per day split by status
class, the data sent back, average CPU and memory for this month and today, the cost so far this month, a forecast for
this month and next, daily charts for the last 31 days, and CPU, memory and ready replicas over the last 12 hours. The same numbers
come from `cloider app usage` and the REST API. CPU and memory are the figures an app is billed on, so this page also
explains how they are measured. Requests, data out, replicas and the 12 hour CPU and memory charts are shown only and
never billed.

## At a glance

| Card or chart | Shows |
| --- | --- |
| **Requests (Today)** | Requests to the app's domains so far today |
| **Requests (This Month)** | Requests since the first of the month |
| **Server Errors (This Month)** | The share of this month's requests answered with a 5xx status, and how many |
| **Data Out (This Month)** | Bytes sent back to clients since the first of the month |
| **CPU & Memory** | CPU and memory per replica, minute by minute, against each replica's limit, last hour by default, up to 12 hours |
| **Ready Replicas** | Replicas ready to serve, minute by minute, and each hour's peak, last hour by default, up to 12 hours |
| **Requests** | Requests per day, stacked by 2xx, 3xx, 4xx and 5xx, last 31 days |
| **Data Out** | Bytes sent back per day, last 31 days |
| **Avg. Usage (This Month)** | Average CPU in cores and memory in GB over the days of this month |
| **Avg. Usage (Today)** | Average CPU and memory so far today |
| **Cost to Date (This Month)** | What the app has cost since the first of the month |
| **Cost Forecast** | The expected cost for **This Month** and **Next Month** at the current usage |
| **CPU Usage** | Average cores per day, last 31 days |
| **Memory Usage** | Average GB per day, last 31 days |
| **Cost** | Cost per day, last 31 days |

A [cron job](/apps/cron-jobs) has no domain, so its tab shows its runs in place of the **Requests** and **Server
Errors** cards and the **Requests**, **Data Out**, **CPU & Memory** and **Ready Replicas** charts:

| Card | Shows |
| --- | --- |
| **Jobs (Today)** | The **Runs** that ended so far today, and the **Run Minutes** they ran |
| **Jobs (This Month)** | The runs that ended since the first of the month, and the minutes they ran |
| **Job Success Rate (This Month)** | The share of this month's runs that succeeded and that failed, and how many of each |

Its **Data Out (This Month)** card stays at `0 B`: data out is counted at the domains, and a cron job has none.

## How are requests counted?

Requests are counted where they enter Cloider, at the ingress in front of every app domain: the subdomain the app was
created with and any [custom domain](/apps/domains) or target pointing at it. Every request is counted, including
the ones the app never sees, such as the `503` a client gets while the app is down or restarting.

- **Requests** is the total. The chart splits it by status class: **2xx** success, **3xx** redirect, **4xx** client error
  and **5xx** server error. WebSocket upgrades (`101`) are in the total only.
- **Data Out** is the size of the responses sent back, headers included, in binary units (1 KB = 1024 bytes).
- Counts are added every minute to the current day, in UTC.
- Days from before requests were counted show no bar.

## How are a cron job's runs counted?

- A run is counted within a minute of ending, on the day it ended, in UTC. A run still going isn't counted yet.
- A run counts as **Succeeded** or **Failed** as the **Runs** tab shows it: it failed when it exited with any code other
  than `0`, was stopped after 12 hours, or never started. A run a pause stops isn't counted.
- **Run Minutes** go from the run's container starting to it finishing, the time a run is
  [billed](/apps/cron-jobs#billing) for. Waiting to start, such as pulling the image, isn't counted.

## How are CPU and memory charted?

The **CPU & Memory** charts show what the app's [replicas](/apps/scaling) use, minute by minute, next to what each one
is allowed. They open on the last hour: pick **3h**, **6h** or **12h** to look further back, and **Refresh** for the
latest minute, which also shows next to each chart's title.

<Screenshot
  src="/img/screenshots/apps/insights-cpu-memory.webp"
  url="/dashboard/apps/blog-a7c2mq"
  alt="The blog app's CPU & Memory card with 6h picked: CPU per replica climbing towards 0.4 vCPU through the morning and dropping each time a replica is added, under a dotted 0.5 vCPU limit, and memory holding around 230 MB under a dotted 512 MB limit, each chart with its Average per Replica and dashed Busiest Replica lines and the latest value next to its title"
  caption="Six hours of CPU and memory: CPU per replica drops when a replica is added and rises when one is removed."
/>

- **CPU** is in vCPU, the unit of the compute settings: `0.25 vCPU` is a quarter of one CPU core. Each point is the
  average over the two minutes before it.
- **Memory** is in MB, the memory the replica's processes hold (its working set), which is what counts towards its
  limit. A replica past its memory limit is restarted.
- With more than one replica, the solid line is the **Average per Replica**, which is what autoscaling compares with
  its target, and the dashed line the **Busiest Replica**. The tooltip adds the total of **All replicas**.
- The dotted **Limit per Replica** line is what each replica can use. It starts hidden when the app uses less than a
  quarter of it, so the usage isn't flattened at the bottom of the chart: click it in the legend to show it.
- The app's own container is measured, not the dashboard's terminal or the app's builds.
- Times are in your browser's time zone. A **paused** app, or a stretch the app wasn't running, shows as a gap.

These are the measurements as they happen, so they move with each spike. The daily **CPU Usage** and **Memory Usage**
charts are the billed averages, and count each replica at no less than what it is given.

## How are replicas counted?

The **Ready Replicas** chart shows how many of the app's [replicas](/apps/scaling) were ready to serve requests, which
is where autoscaling shows: the line climbs when the app scales up and drops when it scales back down. The dashed line
is the most replicas of each hour. It opens on the last hour: pick **3h**, **6h** or **12h** to look further back, and
**Refresh** for the latest count, which also shows next to the title.

<Screenshot
  src="/img/screenshots/apps/insights-replicas.webp"
  url="/dashboard/apps/blog-a7c2mq"
  alt="The blog app's Ready Replicas card with 6h picked and 2 replicas now: a stepped line going from 2 to 3 and 4 through the morning, back to 2 in the early afternoon and briefly to 3 before 15:00, with the dashed Peak per Hour line above it"
  caption="Six hours of autoscaling: up for the midday traffic, down after it, and a short step up for a burst."
/>

- Replicas are counted every minute. Each change of the count and each hour's peak are kept for 12 hours.
- A replica counts once it is ready: when its [health check](/apps/health-checks) passes, or without one, when it
  accepts connections on the app's port. A replica still starting or failing its check isn't counted. A deploy
  doesn't add one: the old replica stops being counted as its replacement takes over.
- A **paused** app has `0`.
- Times are in your browser's time zone.
- A stretch without samples, such as before replicas were counted, shows as a gap.

## How is usage measured?

Each sample adds up the CPU and memory of all the app's running [replicas](/apps/scaling), each counting the larger
of what it is given and what it uses, which is what the app is [billed](/apps/scaling#how-is-a-scaled-app-billed) for.
The terminal that the dashboard's **Terminal** tab opens isn't counted, only your app.

- **CPU** is in cores: `0.25 cores` is a quarter of one CPU core on average.
- **Memory** is in GB.
- Samples are averaged over time, so a short spike barely moves a daily average.
- A **paused** app has no running replicas, so its samples are zero and it costs nothing for compute.

Cost is calculated from the same averages: the larger of the CPU cores used and the memory used converted to cores at a
fixed ratio, times the compute rate, times the time the app ran. The rate is on the [pricing page](/reference/pricing),
and [the billing model](/concepts/billing-model) explains how daily costs become an invoice.

```bash
curl https://cloider.com/api/apps/a7c2mq/usage \
  -H "Authorization: Bearer $CLOIDER_TOKEN"
```

```json title="Response"
{
  "hashed_id": "a7c2mq",
  "app_label": "blog",
  "status": "Ready",
  "daily_usage": [
    {
      "resource_type": "app",
      "date": "2026-10-19T00:00:00Z",
      "total_cost": 0.0947,
      "total_time_seconds": 86400,
      "metrics": {
        "cpu": 38.5,
        "memory": 212.4,
        "compute_cost": 0.0947,
        "requests": 18342,
        "requests_by": {"2xx": 17610, "3xx": 402, "4xx": 318, "5xx": 12},
        "bytes_out": 96468992
      }
    }
  ],
  "monthly_usage": {
    "avg_cpu_usage": 41,
    "avg_memory_usage": 208,
    "compute_total_cost": "1.84",
    "total_cost": 1.84,
    "days": 20,
    "forecast_this_month": 2.91,
    "forecast_next_month": 2.88
  },
  "forecast_rest_of_day": 0.0312,
  "date": "2026-10-20",
  "month": "2026-10"
}
```

`metrics.cpu` and `monthly_usage.avg_cpu_usage` are in millicores (1000 = one core), `metrics.memory` and
`avg_memory_usage` in MiB. `metrics.requests` is the day's request count and `metrics.requests_by` its split by status
class, `metrics.bytes_out` the bytes sent back. Days from before requests were counted have none of the three.
A cron job's days also have `metrics.runs`, the runs that ended, `metrics.runs_failed`, how many of them failed, and
`metrics.run_seconds`, how long they ran, each absent when zero. `daily_usage` holds up to the last 31 days.

A web app's ready replicas over the last 12 hours have their own endpoint:

```bash
curl https://cloider.com/api/apps/a7c2mq/replicas/history \
  -H "Authorization: Bearer $CLOIDER_TOKEN"
```

A trimmed example:

```json title="Response"
{
  "changes": [
    {"at": 1794229200, "replicas": 2},
    {"at": 1794240660, "replicas": 3},
    {"at": 1794241500, "replicas": 2}
  ],
  "hourly_peaks": [{"hour": 1794240000, "peak": 3}, {"hour": 1794243600, "peak": 2}],
  "last_sample_at": 1794248535
}
```

`changes` lists each time the count changed, oldest first, `at` in Unix seconds. The first can be the count already
standing 12 hours ago, and `replicas` is `null` from a sample that was missed until the next one. `hourly_peaks` has
the most replicas of each hour, `hour` being its start, and `last_sample_at` the latest sample, which the last change
holds until.

Its CPU and memory over the last 12 hours, a point a minute:

```bash
curl https://cloider.com/api/apps/a7c2mq/metrics \
  -H "Authorization: Bearer $CLOIDER_TOKEN"
```

A trimmed example:

```json title="Response"
{
  "start": 1794206160,
  "step": 60,
  "replicas": [2, 2, 3],
  "cpu": {
    "average": [41.2, 44.8, 52.1],
    "busiest": [47.9, 51.3, 66.4],
    "total": [82.4, 89.6, 156.3],
    "limit": [250, 250, 250]
  },
  "memory": {
    "average": [188.4, 190.1, 176.9],
    "busiest": [201.7, 203.2, 204.5],
    "total": [376.8, 380.2, 530.7],
    "limit": [500, 500, 500]
  }
}
```

The first point is at `start`, in Unix seconds, and each next one `step` seconds later, up to the current minute, so
every array has 721 values. `replicas` is how many were measured at each point. `cpu` is in millicores (1000 = one
vCPU) and `memory` in MiB, per replica on average, for the busiest replica, for all of them together, and the limit
each one has. A value is `null` where no replica ran, and `limit` where the replicas had none.

## Use insights to size and save

- **Ready replicas sit at the maximum**: the autoscaler wants more than it is allowed. Raise the maximum, or give each
  replica more CPU or memory, under [compute](/apps/scaling).
- **5xx share goes up**: the app is failing requests. Check the [logs](/apps/logs) around the days it rose.
- **Memory climbs towards its limit on the CPU & Memory chart**: the replica restarts when it gets there. Give each
  replica more memory under [compute](/apps/scaling), or look for what holds on to it.
- **Memory climbs day after day**: the app probably leaks memory. Check the [logs](/apps/logs) and restart it by saving
  the **Environment** tab, then fix the leak.
- **High CPU at idle**: look for busy loops, aggressive polling or a development server running in production (for
  example `npm run dev` instead of `npm start`).
- **An app nobody uses**: [pause it](/apps/pause-resume-and-delete). A paused app costs nothing for compute and keeps its
  configuration.

For a single process rather than the whole replica, look inside the container, if its image has `ps`:

```bash
cloider app exec blog -- ps aux
```
