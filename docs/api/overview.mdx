The Cloider REST API is the HTTP interface behind the dashboard, the `cloider` CLI, the Terraform provider and the MCP server. Everything those tools do, you can do with plain HTTPS requests that send and receive JSON: create a Kubernetes cluster, deploy an app, resize a database, upload a file to a bucket or add a DNS record.

This page explains the conventions every endpoint follows, walks you through a first request, and lists every endpoint with a link to its reference page.

## At a glance

| | |
| --- | --- |
| **Base URL** | `https://cloider.com/api` |
| **Protocol** | HTTPS only. JSON request and response bodies, with a few plain text and streaming exceptions listed below |
| **Authentication** | An API token in the `Authorization: Bearer cldr_...` header. See [Authentication](/api/authentication) |
| **Token scope** | One account per token, with Read or Read & Write access |
| **Resource ids** | Short opaque ids such as `k3x9p` (`hashed_id`), domain names for domains, numeric ids for DNS records |
| **Errors** | JSON `{"errors": {"field": ["message"]}, "data": null}`, with general messages under `_`. See [Errors](/api/errors) |
| **Rate limits** | 10 requests a second and 100 requests a minute per client. See [Rate limits](/api/rate-limits) |
| **Long running work** | Create, pause, resume, restore and delete answer at once; poll the resource's `/status` endpoint until it settles |
| **Versioning** | One unversioned API. The CLI, Terraform provider and dashboard use the same routes you do |

## Who should use the API?

Use the REST API when you write your own integration: an internal tool, a deployment script in a language without a Cloider SDK, a chatbot, or a CI system where installing the CLI isn't practical. Every request is an ordinary HTTPS call, so any language with an HTTP client works.

If one of the higher level tools fits, it is usually less work:

| Tool | When it is the better choice |
| --- | --- |
| [CLI](/cli/overview) | Shell scripts and CI jobs. It resolves names to ids, waits for operations and retries rate limits for you |
| [Terraform](/terraform/overview) | Declaring clusters, databases, buckets, registries, domains and DNS as code that is reviewed and applied |
| [MCP server](/mcp/overview) | Letting an AI agent such as Claude or Cursor manage your resources |

All of them call the endpoints documented here, so anything you learn on these pages applies to them too.

## Base URL

Every endpoint lives under one base URL:

```text
https://cloider.com/api
```

The paths in this reference are relative to it. `GET /clusters` means:

```bash
curl https://cloider.com/api/clusters \
  -H "Authorization: Bearer $CLOIDER_TOKEN"
```

There is no version segment in the path and no regional endpoint. Object storage, the container registry and your databases have endpoints of their own (an S3 endpoint per bucket region, `registry.cloider.com`, a host per database), and the API tells you what they are in each resource's response.

## Make your first request

The quickest way to check that your token works is `GET /whoami`, which tells you who the token acts as and in which account.

### 1. Create an API token

Open **Access Control** in the dashboard, go to the **API Tokens** tab and create a token. Pick **Read** for a token that only looks, or **Read & Write** for one that can change things. The token is shown once, so copy it right away. [API tokens](/account/api-tokens) walks through it with screenshots.

### 2. Keep the token in an environment variable

```bash
export CLOIDER_TOKEN=cldr_xxxxxxxxxxxxxxxxxxxxxxxx
```

`CLOIDER_TOKEN` is the variable every example in these docs uses, and the one the CLI reads, so the same variable serves both.

### 4. List something

With the token working, list the account's Kubernetes clusters:

```bash
curl https://cloider.com/api/clusters \
  -H "Authorization: Bearer $CLOIDER_TOKEN"
```

```json title="Response"
[
  {
    "hashed_id": "k3x9p",
    "cluster_name": "staging",
    "cluster_label": "staging",
    "cluster_version": "1.34",
    "is_ha": false,
    "status": "Ready",
    "created_at": "2026-10-12T10:22:41.502113Z"
  }
]
```

The `hashed_id` is what every other cluster endpoint takes in its path, for example `GET /clusters/k3x9p/status`.

## Request conventions

### Headers

| Header | When | Value |
| --- | --- | --- |
| `Authorization` | Every request except `GET /pricing` | `Bearer cldr_...` |
| `Content-Type` | Requests with a JSON body (`POST`, `PUT`, some `DELETE`) | `application/json` |
| `Accept` | Streaming endpoints | `text/event-stream` (optional, the stream is sent either way) |
| `Last-Event-ID` | Reconnecting to a build log stream | The `id` of the last event you received |

### Request bodies

Write endpoints take a JSON object. Field names are `snake_case`, the same names the API uses in its responses (`cluster_name`, `database_plan`, `read_only`). A field you leave out takes its zero value: an empty string, `0`, `false` or an empty list. The reference page of each endpoint marks which fields are required and what the defaults are.

A few `DELETE` endpoints take a JSON body too, for example `DELETE /apps/:hashed_id` takes the free subdomains to delete with the app. Most HTTP clients support a body on `DELETE`; with curl, pass `-d` as usual.

### Query parameters

Filters, pagination and a few ids travel in the query string, for example `GET /buckets/k3x9p/objects?prefix=images/` or `GET /database/password?id=d7f2m`. URL encode values that contain `/`, spaces or other reserved characters (`curl -G --data-urlencode` does this for you).

### CORS

The API sends permissive CORS headers, so a browser can call it from any origin. That doesn't make it a good idea to put a token in a public web page: anyone who opens the page can read the token. Call the API from a server, a script or CI, and keep tokens in secrets.

## How resources are identified

Most resources have a short, opaque id called `hashed_id`, made of lower case letters and digits (for example `k3x9p`). It is in every list and create response, and it is what the path parameters named `:hashed_id` expect. The API does not look resources up by name: pass the id. The CLI and Terraform accept names because they list the resources first and pick the matching id for you.

| Resource | Identified in paths by | Example |
| --- | --- | --- |
| Clusters, databases, apps, buckets | `hashed_id` | `/clusters/k3x9p`, `/apps/a8q2w` |
| Bucket keys, registry tokens, targets | `hashed_id` | `/bucket-keys/b5n1t` |
| Registry projects | `hashed_id` | `/registry/projects/r4c8z` |
| App builds | the build's `hashed_id`, under the app | `/apps/a8q2w/builds/u9e3k/logs` |
| Git connections | the installation's `hashed_id` | `/git/github/installations/g2h6v/repos` |
| Support tickets and attachments | `hashed_id`, in upper case | `/support/tickets/K7Q2M` |
| Domains | the domain name itself | `/domains/example.com` |
| DNS records | the record's numeric `id` | `/dns-records/1042` |
| Registry immutability rules, retention runs and tasks | the numeric `id` from their list endpoint | `/registry/projects/r4c8z/retention/runs/57` |
| Uploaded app source | the `source_token` the upload returned | `/apps/source/<token>` |

Three database endpoints take the id in the query string instead of the path: `GET /database/password?id=...`, `GET /database/cert?id=...` and `GET /database/backups?id=...`.

### Names, labels and ids

Clusters, databases and apps also have a **name** you choose and a **label** that is unique in the account. Names don't have to be unique: if the account already has a cluster named `staging`, a second one gets the label `staging-1`. The dashboard and CLI show the label; the API returns both (`cluster_name` and `cluster_label`, `database_name` and `database_label`, `app_name` and `app_label`). Only the `hashed_id` is guaranteed never to change.

## Response conventions

### Successful responses

A successful response is the resource itself, not wrapped in an envelope. A list endpoint answers with a JSON array, a single resource with a JSON object:

```json
[{"hashed_id": "k3x9p", "cluster_name": "staging", "status": "Ready"}]
```

Some write endpoints answer with the updated list of things you just changed (for example changing a bucket key returns every key of the account), so you can refresh a view without a second request. Each endpoint's page shows its exact response.

A list that has nothing in it is `[]`, never `null`, and a JSON object with no keys is `{}`.

### Plain text responses

A handful of endpoints answer with plain text because that is what you want to save or compare:

| Endpoint | Body |
| --- | --- |
| `GET /clusters/:hashed_id/status` (and the same for databases, buckets, registry projects, apps) | The status word, for example `Ready` |
| `GET /clusters/:hashed_id/kubeconfig` | The kubeconfig YAML file |
| `GET /database/password` | The database password |
| `GET /database/cert` | The CA certificate in PEM format |
| `GET /apps/:hashed_id/builds/:build_hashed_id/logs` | The build log |

### Streaming responses

Logs are streamed as [server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events) (`text/event-stream`): `GET /apps/:hashed_id/logs/stream` for a running app and `GET /apps/:hashed_id/builds/:build_hashed_id/logs/stream` for a build. The exec endpoints (`POST /clusters/:hashed_id/exec` and the database and app equivalents) also answer with an event stream. Read them with `curl -N` so curl doesn't buffer the output. [Apps](/api/endpoints/apps#stream-an-apps-logs) and [App builds](/api/endpoints/app-builds) show the event format.

### Redirects and presigned URLs

Large files never pass through the API. To upload or download a bucket object, an app's source archive or a support attachment, the API hands you a short lived **presigned URL** on the storage service, and you send the bytes there directly. Most endpoints return the URL in their JSON answer; the support attachment download answers with a `302` redirect to it instead, so pass `-L` to curl to follow it. The flows are described step by step on [Bucket objects](/api/endpoints/bucket-objects), [Apps](/api/endpoints/apps) and [Support](/api/endpoints/support).

### Field types

| JSON type | Used for | Example |
| --- | --- | --- |
| string | ids, names, statuses, enums | `"hashed_id": "k3x9p"`, `"status": "Ready"` |
| string, RFC 3339 timestamp | `created_at`, `updated_at`, `last_used_at` and other times | `"2026-10-12T10:22:41.502113Z"` |
| string, month name | the month of a bill or of usage figures | `"month": "October 2026"` |
| number | sizes in bytes, ports, counts, amounts of money | `"size_bytes": 1048576`, `"total_cost": 4.27` |
| boolean | flags | `"read_only": true` |
| `null` | an optional value that isn't set | `"last_used_at": null` |

Timestamps carry fractional seconds and a time zone offset, so parse them with an RFC 3339 parser rather than a fixed format. Days in usage figures are timestamps at midnight, for example `"date": "2026-10-19T00:00:00Z"`. Amounts of money are plain JSON numbers in the account's billing currency.

### Statuses

Resources that take time to provision have a `status`. Clusters, databases and apps share these values:

| Status | Meaning |
| --- | --- |
| `Creating`, `Starting` | Being provisioned or started |
| `Ready` | Running and usable |
| `Pausing`, `Paused` | Being stopped, or stopped with its data kept |
| `Upgrading` | A change, such as a database resize, is being applied |
| `Terminating`, `Terminated` | Being deleted, or deleted |
| `Failed` | Provisioning or an operation failed |

Apps and their builds use a few more (`Pending`, `Queued`, `Building`, `Deploying`, `Superseded`, `Canceled`). [Status values](/reference/status-values) lists every status of every product.

## Long running operations

Creating, pausing, resuming, restoring and deleting a resource takes from seconds to minutes. These endpoints don't wait: they accept the request, start the work and answer right away, usually with the resource in a transitional status such as `Creating` or `Pausing`. You then poll the resource's status endpoint until it reaches the status you want.

```bash title="Wait for a new cluster to become Ready"
until [ "$(curl -s https://cloider.com/api/clusters/k3x9p/status \
  -H "Authorization: Bearer $CLOIDER_TOKEN")" = "Ready" ]; do
  sleep 5
done
echo "Cluster is ready"
```

Poll every few seconds, not in a tight loop: every poll counts against the [rate limit](/api/rate-limits). Stop when the status is `Failed` too. The CLI's `--wait` flag does exactly this.

| Operation | Endpoint to poll | Done when |
| --- | --- | --- |
| Create or resume a cluster | `GET /clusters/:hashed_id/status` | `Ready` |
| Pause a cluster | `GET /clusters/:hashed_id/status` | `Paused` |
| Create, resume, resize or restore a database | `GET /databases/:hashed_id/status` | `Ready` |
| Create a bucket | `GET /buckets/:hashed_id/status` | `Ready` |
| Create a registry project | `GET /registry/projects/:hashed_id/status` | `Ready` |
| Deploy an app | `GET /apps/:hashed_id/builds` (the build's `status`) | `Ready` or `Failed` |
| Delete a cluster, database or app | its status endpoint | `Terminated` |
| Delete a bucket or registry project | its status endpoint | `404` |

## Retries and idempotency

The API has no idempotency keys, so a request that is sent twice runs twice. Follow these rules, which are the ones the CLI applies:

- **Reads** (`GET`) are always safe to retry, including after a timeout or a `502`, `503` or `504`.
- **A `429 Too Many Requests`** means the request was turned away before it reached the API, so it is safe to retry any request after waiting. See [Rate limits](/api/rate-limits).
- **Writes** (`POST`, `PUT`, `DELETE`) that timed out or failed with a `5xx` may have gone through. Read the resource back before you try again. A second `POST /clusters` with the same name, for example, creates a second cluster labelled `staging-1` rather than failing.
- **`PUT` endpoints** replace a setting with the value you send (trusted sources, environment variables, lifecycle rules), so sending the same body again leaves the same result.

## Roles and permissions

A token can never do more than the member who created it can do in the account, and its access is checked on every request. If the member is removed or deactivated, their tokens stop working at once; if they are made `Restricted`, their tokens become read only. [Authentication](/api/authentication) has the details, and [Accounts and roles](/concepts/accounts-and-roles) explains the roles.

## What the API doesn't cover

- **Signing in and connecting git providers.** Signing in to the dashboard and connecting GitHub, GitLab or Bitbucket happen in the browser, so an API token can't do them. Once a provider is connected, Cloider picks up its pushes by itself.
- **Members and API tokens.** Inviting and removing members, changing their roles, and creating, changing or deleting API tokens are done in the dashboard only, so a leaked token can't hand out more access. You can list members and tokens, and a token can revoke itself. See [Authentication](/api/authentication#which-endpoints-are-dashboard-only).
- **The workloads themselves.** Inside a Kubernetes cluster you use the standard Kubernetes API with the cluster's kubeconfig; inside a bucket, any S3 client; inside the registry, `docker`; inside a database, its own client. The Cloider API manages the resources, not what runs in them.
