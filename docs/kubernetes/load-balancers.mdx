A load balancer gives a Kubernetes Service its own public IP address. On Cloider you create one the standard Kubernetes way, with a Service of `type: LoadBalancer`: the cluster assigns it an external IP, traffic to that IP on the Service's ports reaches your pods, and the load balancer is billed for the time it exists. This page shows how to create one, point a domain at it, and keep track of what it costs.

## At a glance

| | |
| --- | --- |
| **How to create one** | A Service with `spec.type: LoadBalancer` |
| **What you get** | An external IP in the Service's `status.loadBalancer.ingress`, shown as `EXTERNAL-IP` by `kubectl get svc` |
| **Protocols** | The Service's ports, TCP or UDP |
| **TLS** | Passed through untouched. Your app terminates TLS itself |
| **Billing** | Per load balancer per month, prorated to the second while the Service has an external IP. See [pricing](https://cloider.com/#pricing) |
| **Where to see the cost** | **Usage** in the dashboard, **LoadBalancers Usage** table of each cluster |

## Load balancer or domain target?

Cloider has two ways to make a Service reachable from the internet. Pick by protocol:

| | Domain [target](/kubernetes/expose-services) | `type: LoadBalancer` |
| --- | --- | --- |
| **Traffic** | HTTP and HTTPS | Any TCP or UDP port |
| **Address** | Your domain or a free `*.cloider.app` subdomain | A public IP |
| **HTTPS certificate** | Automatic | Your app's job |
| **Several services on one address** | Yes, by path (`/`, `/api`, ...) | One IP per Service |
| **Cost** | No load balancer charge | Billed per load balancer |
| **Typical use** | Websites, APIs, dashboards | Databases you run yourself, MQTT, game servers, SMTP, gRPC without HTTP routing, custom TCP protocols |

For a website or an HTTP API, a target is simpler and cheaper. Use a load balancer when you need a raw port.

## Create a load balancer

This example publishes an [MQTT broker](https://mosquitto.org/) (Eclipse Mosquitto) on TCP port 1883.

```yaml title="mqtt.yaml"
apiVersion: v1
kind: Namespace
metadata:
  name: iot
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: mosquitto-config
  namespace: iot
data:
  mosquitto.conf: |
    listener 1883
    allow_anonymous true
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mqtt
  namespace: iot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mqtt
  template:
    metadata:
      labels:
        app: mqtt
    spec:
      containers:
        - name: mosquitto
          image: eclipse-mosquitto:2.0.18
          ports:
            - name: mqtt
              containerPort: 1883
          volumeMounts:
            - name: config
              mountPath: /mosquitto/config
          resources:
            requests:
              cpu: 25m
              memory: 32Mi
      volumes:
        - name: config
          configMap:
            name: mosquitto-config
---
apiVersion: v1
kind: Service
metadata:
  name: mqtt
  namespace: iot
spec:
  type: LoadBalancer
  selector:
    app: mqtt
  ports:
    - name: mqtt
      port: 1883
      targetPort: mqtt
      protocol: TCP
```

:::warning[Open to the internet]
A LoadBalancer Service is reachable by anyone on the internet. The example allows anonymous access to keep it short; in production configure authentication in the application itself.
:::

## Test the connection

From your computer, with an MQTT client such as `mosquitto_sub` and `mosquitto_pub`:

```bash
mosquitto_sub -h 203.0.113.25 -p 1883 -t test &
mosquitto_pub -h 203.0.113.25 -p 1883 -t test -m "hello from cloider"
```

For any TCP service, `nc` tells you whether the port is open:

```bash
nc -vz 203.0.113.25 1883
```

## Point a domain at the load balancer

Give the IP a name with an `A` record. If the domain's DNS is hosted on Cloider (see [Domains and DNS](/domains/overview)):

```bash
cloider dns create example.com --type A --name mqtt --value 203.0.113.25 --ttl 300
```

Clients then connect to `mqtt.example.com:1883`. See [DNS records](/domains/dns-records) for the dashboard and other tools.

:::note[Keep the Service to keep the IP]
The external IP belongs to the Service. If you delete the Service and create it again, it can get a different IP, and your `A` record must be updated. To change ports or selectors, edit the Service in place (`kubectl apply`) rather than deleting it.
:::

## Several ports on one load balancer

One Service can expose several ports on the same IP, and it is still one load balancer:

```yaml title="game-server-service.yaml"
apiVersion: v1
kind: Service
metadata:
  name: game
  namespace: games
spec:
  type: LoadBalancer
  selector:
    app: game
  ports:
    - name: game-udp
      port: 7777
      targetPort: 7777
      protocol: UDP
    - name: query
      port: 27015
      targetPort: 27015
      protocol: TCP
```

Every additional Service of type `LoadBalancer` is an additional load balancer with its own IP and its own charge.

## How are load balancers billed?

A load balancer is billed per load balancer per month, prorated to the second, for as long as its Service has an external IP. A month is counted as 30 days. The current price is on the [pricing page](https://cloider.com/#pricing), in [Pricing](/reference/pricing) and in the output of `cloider pricing`.

- **The meter starts** when the Service gets its external IP, and **stops** when the Service is deleted or changed to another type.
- **A Service that stays `<pending>`** has no IP and isn't billed.
- **Load balancers are counted by name** (`<namespace>/<service>`). If a Service of the same name is recreated, its time keeps adding to the same entry, and the entry records how many times it was recreated.
- **A load balancer is billed whatever the cluster's status**, so delete LoadBalancer Services you don't need. See [Pause and resume](/kubernetes/pause-and-resume).

## List services and stop a load balancer

List every LoadBalancer Service in a cluster with its IP:

```bash
kubectl get services -A | grep -E "NAMESPACE|LoadBalancer"
```

Stop paying for one by deleting the Service, or by switching it to `ClusterIP` and publishing it with a [target](/kubernetes/expose-services) instead:

```bash
kubectl delete service mqtt -n iot
# or
kubectl patch service mqtt -n iot -p '{"spec": {"type": "ClusterIP"}}'
```

## Troubleshooting

**`EXTERNAL-IP` stays `<pending>`**: run `kubectl describe service <name> -n <namespace>` and read the events. If nothing explains it after a few minutes, open a [support request](/account/support) with the cluster id and the Service's name.

**Connection refused or timeout on the IP**: check that the Service's `selector` matches the pods' labels (`kubectl get endpoints <name> -n <namespace>` must list pod IPs), that `targetPort` is the port the container listens on, and that the app listens on `0.0.0.0` and not only on `127.0.0.1`.

**Works for TCP, not for UDP**: check that the Service port has `protocol: UDP` and that the container port matches.

**The IP changed**: the Service was deleted and recreated. Update your DNS record and edit Services in place from now on.

More cases are in [Kubernetes troubleshooting](/kubernetes/troubleshooting).
