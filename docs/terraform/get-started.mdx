This tutorial takes you from nothing to a running Kubernetes cluster and a PostgreSQL database on Cloider, created with Terraform (or OpenTofu). You install the tool, give the Cloider provider an API token, write a small configuration, then run `terraform init`, `plan` and `apply`, use the outputs, change the database, and delete everything with `terraform destroy`. It takes about ten minutes, most of it waiting for the cluster.

## Before you begin

- A Cloider account. See [Create an account](/get-started/create-an-account). The configuration on this page creates one cluster and one database, which fits in the free trial.
- A way to give Terraform an API token: either the [`cloider` CLI](/cli/install), logged in with `cloider login`, or a **Read & Write** [API token](/account/api-tokens) from **Access Control**, **API Tokens** in the dashboard.
- A terminal. `kubectl` is optional, for the step that connects to the cluster (see [Connect with kubectl](/kubernetes/connect-with-kubectl)).

## Step 1: Install Terraform or OpenTofu

The provider works with Terraform 1.0 or later and OpenTofu 1.6 or later. Any of those versions can follow this tutorial, but installing the newest release is recommended (`import` blocks, used in [Import existing resources](/terraform/guides/import-existing-resources), need Terraform 1.5 or later).

<Tabs groupId="os">
<TabItem value="macos" label="macOS" default>

With [Homebrew](https://brew.sh):

```bash
# Terraform
brew tap hashicorp/tap
brew install hashicorp/tap/terraform

# or OpenTofu
brew install opentofu
```

</TabItem>
<TabItem value="linux" label="Linux">

On Debian or Ubuntu, from HashiCorp's apt repository:

```bash
wget -O - https://apt.releases.hashicorp.com/gpg | sudo gpg --dearmor -o /usr/share/keyrings/hashicorp-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] https://apt.releases.hashicorp.com $(lsb_release -cs) main" | sudo tee /etc/apt/sources.list.d/hashicorp.list
sudo apt update && sudo apt install terraform
```

For other distributions, and for OpenTofu, follow the official instructions: [Install Terraform](https://developer.hashicorp.com/terraform/install) or [Install OpenTofu](https://opentofu.org/docs/intro/install/).

</TabItem>
<TabItem value="windows" label="Windows">

With [winget](https://learn.microsoft.com/windows/package-manager/winget/):

```powershell
# Terraform
winget install --exact --id Hashicorp.Terraform

# or OpenTofu
winget install --exact --id OpenTofu.Tofu
```

Or download the zip from [Install Terraform](https://developer.hashicorp.com/terraform/install) and put `terraform.exe` on your `PATH`.

</TabItem>
</Tabs>

Check that it works. The command prints the installed version and your platform:

```bash
terraform version   # or: tofu version
```

:::tip[Using OpenTofu?]
Every command on this page works with OpenTofu: type `tofu` where it says `terraform`, for example `tofu init` and `tofu apply`. The configuration files are the same.
:::

## Step 2: Give the provider an API token

The provider needs a Cloider API token to act on your account. Pick one of these:

<Tabs groupId="token-source">
<TabItem value="cli" label="cloider login" default>

If you use the `cloider` CLI, log in once. The provider reads the token the CLI saved, so you don't have to handle it at all:

```bash
cloider login
```

The browser opens a page where you choose the account and **Read & Write** access. See [CLI authentication](/cli/authentication) for details.

</TabItem>
<TabItem value="env" label="Environment variable">

Create a **Read & Write** token in the dashboard under **Access Control**, **API Tokens**:

<Screenshot
  src="/img/screenshots/account/api-token-create.webp"
  url="/dashboard/access-control"
  alt="The create API token dialog in Access Control, with a name field and the choice between Read and Read & Write access"
  caption="Terraform needs a Read & Write token to apply. A Read token is enough for terraform plan."
/>

Then export it in the terminal you run Terraform from:

```bash
export CLOIDER_TOKEN="cldr_xxxxxxxxxxxxxxxxxxxxxxxx"
```

This is also how you give the provider a token in CI. See [CI/CD with Terraform](/terraform/guides/ci-cd).

</TabItem>
</Tabs>

:::warning[Don't write the token into a .tf file]
A token in a configuration file ends up in git and in every copy of the code. Use `cloider login`, an environment variable or a token file instead. All the options are on [Provider configuration](/terraform/provider-configuration).
:::

## Step 3: Write the configuration

Create an empty folder for the project and three files in it. Terraform reads every `.tf` file in the folder, so how you split them is up to you. This split is a common convention.

```bash
mkdir cloider-staging && cd cloider-staging
```

`versions.tf` says which provider to download:

```hcl title="versions.tf"
terraform {
  required_version = ">= 1.0"

  required_providers {
    cloider = {
      source  = "cloider/cloider"
      version = "~> 0.1"
    }
  }
}
```

`main.tf` declares the provider and the resources. The cluster is called `staging`, and the database `orders-db` only accepts connections from that cluster:

```hcl title="main.tf"
# Takes the token from CLOIDER_TOKEN, or from `cloider login`
provider "cloider" {}

# A serverless Kubernetes cluster
resource "cloider_cluster" "staging" {
  name = "staging"
}

# A PostgreSQL database that only the cluster may connect to
resource "cloider_database" "orders" {
  name            = "orders-db"
  engine          = "postgresql"
  plan            = "hobby"
  trusted_sources = ["cluster:${cloider_cluster.staging.id}"]
}
```

`outputs.tf` prints what you need to connect. Values marked `sensitive` are hidden in the terminal and shown only when you ask for them by name:

```hcl title="outputs.tf"
output "kubeconfig" {
  description = "terraform output -raw kubeconfig > kubeconfig.yaml"
  value       = cloider_cluster.staging.kube_config.raw
  sensitive   = true
}

output "database_host" {
  description = "The host the cluster reaches the database at"
  value       = cloider_database.orders.private_host
}

output "database_port" {
  value = cloider_database.orders.port
}

output "database_user" {
  value = cloider_database.orders.user
}

output "database_password" {
  value     = cloider_database.orders.password
  sensitive = true
}
```

A few things to notice:

- `cloider_cluster.staging.id` refers to the cluster's id, which only exists after the cluster is created. Terraform sees that reference and creates the cluster before the database.
- `trusted_sources` would default to `["*"]` (anywhere). Here it lists only the cluster. See [Trusted sources](/databases/trusted-sources).
- `private_host` is the host for clients running inside Cloider, such as pods in the cluster. Your laptop uses `host` instead. See [Connect to a database](/databases/connect).

## Step 4: Initialize the folder

`terraform init` downloads the Cloider provider from the registry into `.terraform/` and writes `.terraform.lock.hcl`:

```bash
terraform init
```

```text title="Output"
Initializing the backend...
Initializing provider plugins...
- Finding cloider/cloider versions matching "~> 0.1"...
- Installing cloider/cloider v0.1.x...
- Installed cloider/cloider v0.1.x (self-signed, key ID XXXXXXXXXXXXXXXX)

Terraform has created a lock file .terraform.lock.hcl to record the provider
selections it made above. Include this file in your version control repository
so that Terraform can guarantee to make the same selections by default when
you run "terraform init" in the future.

Terraform has been successfully initialized!
```

`v0.1.x` is the newest 0.1 release on the day you run it. Commit `.terraform.lock.hcl` with your `.tf` files, and add `.terraform/` and `*.tfstate*` to `.gitignore`.

## Step 6: Create the resources

`terraform apply` shows the same plan and asks for confirmation. Type `yes`:

```bash
terraform apply
```


The provider creates the cluster and waits until its status is `Ready`, then does the same for the database. Each wait is limited to 20 minutes, see [timeouts](/terraform/resources/cluster#timeouts).

Terraform has now written `terraform.tfstate` in the folder. It records the ids of what it created, and also the database password and the cluster's kubeconfig, so treat it like a password. For anything beyond a test, keep state in a remote backend such as a [Cloider bucket](/terraform/guides/state-backend).

## Step 7: Use the outputs

Print every output, or one by name. `-raw` prints a string without quotes, which is what you want for files and scripts:

```bash
terraform output
terraform output -raw database_password
```

Save the kubeconfig and talk to the cluster with `kubectl`:

```bash
terraform output -raw kubeconfig > kubeconfig.yaml
chmod 600 kubeconfig.yaml
KUBECONFIG=./kubeconfig.yaml kubectl get namespaces
```

```text title="Output"
NAME              STATUS   AGE
default           Active   4m
kube-node-lease   Active   4m
kube-public       Active   4m
kube-system       Active   4m
```

The resources are ordinary Cloider resources, so you also see them in the dashboard and the CLI:

```bash
cloider cluster list
cloider db get orders-db
```

From here, a common next step is to deploy into the cluster from the same configuration with the `kubernetes` and `helm` providers, passing the database credentials as a Kubernetes Secret. The [Kubernetes and Helm guide](/terraform/guides/kubernetes-and-helm) shows how.

## Step 8: Change something

Terraform's job is to keep your account matching the configuration. Change the database's plan from `hobby` to `starter` in `main.tf`:

```hcl title="main.tf"
resource "cloider_database" "orders" {
  name            = "orders-db"
  engine          = "postgresql"
  # highlight-next-line
  plan            = "starter"
  trusted_sources = ["cluster:${cloider_cluster.staging.id}"]
}
```

```bash
terraform plan
```

```text title="Output"
cloider_cluster.staging: Refreshing state... [id=x8f2kq]
cloider_database.orders: Refreshing state... [id=p0q9zm]

Terraform used the selected providers to generate the following execution
plan. Resource actions are indicated with the following symbols:
  ~ update in-place

Terraform will perform the following actions:

  # cloider_database.orders will be updated in-place
  ~ resource "cloider_database" "orders" {
      ~ ca_certificate  = (sensitive value)
        id              = "p0q9zm"
        name            = "orders-db"
      ~ plan            = "hobby" -> "starter"
      ~ status          = "Ready" -> (known after apply)
        # (13 unchanged attributes hidden)
    }

Plan: 0 to add, 1 to change, 0 to destroy.
```

`update in-place` means the database is resized and keeps its data. It restarts once, and `terraform apply` waits until it is `Ready` again. Some changes can't be made in place and **replace** the resource instead (delete it and create a new one): for example a smaller plan, another engine version, or a new name. Terraform marks those `-/+ destroy and then create replacement` and adds `# forces replacement` next to the attribute. Always read the plan before typing `yes`. Every resource page lists which attributes force a replacement, for example [`cloider_database`](/terraform/resources/database#what-replaces-a-database).

Apply the change with `terraform apply`, or put `plan` back to `hobby` and skip it.

## Step 9: Destroy everything

When you are done, delete what the configuration created:

```bash
terraform destroy
```

```text title="Output"

cloider_database.orders: Refreshing state... [id=p0q9zm]

      - engine          = "postgresql" -> null
      - id              = "p0q9zm" -> null
```

Terraform deletes the database first, because it depends on the cluster, and waits for each to be gone. Deleting is permanent: the database's data and everything in the cluster are deleted with them. Billing stops when the resources are deleted.

## Verify

- `terraform apply` ends with `Apply complete! Resources: 2 added`.
- `cloider cluster list` and `cloider db list` show `staging` and `orders-db` with the status `Ready`, as does the dashboard.
- `KUBECONFIG=./kubeconfig.yaml kubectl get namespaces` lists the cluster's namespaces.
- A second `terraform plan` right after the apply says `No changes. Your infrastructure matches the configuration.`

## Troubleshooting

| Error | Cause | Fix |
| --- | --- | --- |
| `No Cloider API token` with `no API token: set token or CLOIDER_TOKEN, or run 'cloider login'` | The provider found no token in any of its sources | Run `cloider login`, or `export CLOIDER_TOKEN=...` in the same terminal |
| `Cloider refused the API token` | The token is mistyped, revoked or expired | Create a new token, or run `cloider login` again |
| `Can't create the cluster` with `Free plan users can not create more than one cluster. UPGRADE NOW!` | The trial allows one cluster, database, bucket and registry project at a time | Delete the other one, or upgrade. See [Limits and quotas](/reference/limits-and-quotas) |
| `This API token is read only!` when applying, while `plan` works | The token is a **Read** token | Use a **Read & Write** token for `apply` and `destroy` |
| `Cluster staging didn't become ready` with `gave up waiting, raise the timeout with a timeouts block` | The cluster took longer than the 20 minute default | Add `timeouts = { create = "40m" }`. The cluster stays in state as tainted, so the next apply replaces it, or run `terraform untaint cloider_cluster.staging` once it is `Ready` |
| `Failed to query available provider packages` during `init` | Typo in `source`, or no access to the registry | Use `source = "cloider/cloider"` and check that the machine can reach `registry.terraform.io` (or `registry.opentofu.org` with OpenTofu) |
